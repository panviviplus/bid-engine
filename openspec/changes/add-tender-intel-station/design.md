# Design

## Context

标擎后端为 Go（Gin + GORM/gen，分层为 `pkg/handler/<模块>` + `pkg/repo/<模块>`），异步任务走 Redis 队列（`pkg/repo/taskqueue`，每个模块独立队列，队列参数在 `conf-local.yml`），定时任务复用 `pkg/middleware/schedule`；前端为 Next.js App Router + Chakra UI，左导航集中在 `router/index.ts`。数据库为本地 MySQL 8（库 `smart-bid`），全库禁止外键。已有基础容器：Redis、MinIO、Docling、Doc-Converter。

参考对象是另一套产品里的 Node 单文件爬虫（固定站点正则 + 两层筛选 + 邮件推送）。本次只借用「站点清单驱动 + 分层筛选 + 通用打标」的思路，不迁移其代码、收件人配置与中标链路。

## Goals / Non-Goals

**Goals**

- 用「接口优先 + 通用抽取 + 浏览器兜底」替换逐站正则，把新站点接入成本降到接近零。
- 采集、理解、分发三层解耦：采集服务无状态无凭据；后端负责清洗、打标、入库、匹配、提醒。
- 后台 LLM 环节与用户级模型配置彻底解耦，避免用户配置影响平台级任务。

**Non-Goals**

- 不追求与参考实现等价的中标公告、邮件推送、附件下载能力。
- 不在本期内引入搜索引擎或全文检索中间件。
- 不做用户自建采集源与多租户数据隔离。

## Decisions

### 采集服务独立部署，Python + FastAPI + Playwright

采集是「高频调用、需要稳定能力、需要浏览器」的工作负载，适合独立服务：可单独扩容、重启与限流，不拖累后端主进程。选 Python 而非 Go：Playwright 在 Python 侧与 Node 侧能力等价，且通用正文抽取（trafilatura / readability）生态成熟，能显著降低自研成本；Go 的 chromedp + go-readability 在反爬兼容与抽取质量上弱一档。服务只暴露 HTTP，不连数据库、不持存储凭据，原始页面快照由后端按需转存 MinIO。

### 发现分级：接口 → 列表页 → 浏览器 → 搜索 API

国内公共资源交易与政府采购平台大量存在站内 JSON 查询接口，稳定性远高于 HTML 列表解析。因此把「站点规则」上升为「源适配器 + 参数」，只对少数必须渲染的源启用浏览器；搜索 API 仅预留接口，本期不启用。规则以 `recipes/*.json` 随服务代码版本管理，避免规则散落在数据库里无法评审。

### 队列与调度：两段式任务 + cron 轮次 + Redis 锁

采集（网络型）与打标入库（LLM 型）资源特征不同，拆成 `tender_intel_collect` 与 `tender_intel_enrich` 两个队列，分别限流。cron 每日多轮生成 `run_id`，每源一个采集任务（幂等键 `run_id + source_key`），轮次内全部源结束后统一触发一次打标，使 LLM 调用可以按批（20 条）合并，成本可控。多实例部署时用 Redis 锁保证同一轮只被触发一次。

### 全局模型配置独立成表

采集打标是平台级后台任务，没有用户上下文。沿用用户级 `user_llm_config` 会引入「用谁的配置」的语义歧义，因此新建 `system_llm_config` 平表：按 `sort` 升序取第一条字段完整的配置，失败自动降级到下一候选，DB 无候选时回落配置文件默认值。选取规则简单、可预测、可观测。

### 打标失败不阻塞入库

采集成果是有限资源，LLM 是易失败环节。因此公告先落库（可能未打标），再由打标阶段补齐行业标签与结构化字段；失败时保留未打标状态并记录批次错误，后续轮次或手动重试补齐。

### 检索先用数据库能力

180 天、十余个源的量级用 MySQL 足以支撑：列表以 `publish_date + id` 为主索引，关键词走标题/正文匹配并配合时间窗；行业筛选通过 `tender_intel_notice_industry` 关联表 + 索引实现。ngram 全文索引作为后续可选优化，不在本期引入。

## Risks / Trade-offs

- [站点结构频繁变化导致抽取质量波动] → 抽取策略与告警写入公告记录，批次页可按源观察成功率；失败源可通过 `/probe` 快速定位。
- [接口型站点存在未公开参数或鉴权] → 先用 `/probe` 验证再落 recipe；验证不通过按同类站点顺序补位，不阻塞整体链路。
- [全行业全量落库带来数据量增长] → 保留期设为 180 天并由定时任务清理，原始快照仅留 30 天。
- [Playwright 容器资源占用较高] → 浏览器上下文并发上限 2–3，仅对声明需要的源启用，其余走 HTTP。
- [LLM 批量打标的标签一致性] → 打标集中在后端单点实现，提示词与行业枚举在代码中版本化，便于回归与批量重跑。

## Migration Plan

1. 建表（无外键）并生成 GORM 代码；本地 MySQL 直接执行。
2. 部署采集服务容器（端口 5011），`start.sh` 增加健康检查提醒。
3. 部署后端（新增队列、路由、调度），随后部署前端。
4. 灰度：仅启用少量源，观察采集批次与打标成功率，再逐步扩大启用源。
5. 回滚：停用源与定时任务即可停止采集；新建表与页面可保留，不影响既有模块。
